native Siril Python script. This document is the output of Phase 1 (research only — no
application code). Every API claim below is either **CONFIRMED** (verified against
official documentation or actual Siril/`sirilpy` source code, cited) or explicitly
flagged **NOT CONFIRMED** / **PARTIALLY CONFIRMED**. Nothing here should be treated as
load-bearing unless marked CONFIRMED.

## 2. GUI Recommendation: PyQt6

Confirmed directly from the official contributor guide (`authors.html`, verbatim):

> "If you want to implement a GUI in your script you should use the pyQt6 toolkit."
> "Scripts using GTK GUIs will not be accepted into the scripts repository."
> `tkinter` support (`tksiril`, `tkfilebrowser`) "will be removed during the 1.5
> development cycle and will be removed before 1.6.0."

Note a real inconsistency we discovered: the **only official GUI script templates**
(`gui_template.py`, `gui_and_args_template.py`) still use **Tkinter**, not PyQt6, and run
synchronously with no threading. There is currently no official PyQt6 template. This
means our architectural patterns for GUI structure, threading, and settings must come
from real, shipped third-party scripts rather than the official templates — see §5.

**Decision: PyQt6**, per the mandatory toolkit rule and per every actively-maintained,
non-trivial script surveyed (see §5). Confirmed, not merely inferred.

## 3. Image Access

`sirilpy.SirilInterface` is the entry point:

```python
import sirilpy as s
siril = s.SirilInterface()
siril.connect()          # raises SirilConnectionError on failure
# ... work ...
# disconnect() is called automatically via atexit — no manual cleanup required
```

Key confirmed methods:

- `siril.is_image_loaded() -> bool`
- `siril.get_image_shape() -> Optional[Tuple[int,int,int]]` — returns **(channels, height, width)**
- `siril.get_image(with_pixels=True, preview=False) -> Optional[FFit]` — `FFit` is
  Siril's own FITS-equivalent object, **not** interchangeable with `astropy.io.fits`.
  `FFit.data.shape` uses **(height, width, channels)** ordering — the *opposite* channel
  position from `get_image_shape()`. This discrepancy is real and must be handled
  explicitly in our image-loading code, not assumed away.
- `siril.get_image_pixeldata(shape=None, preview=False, linked=False) -> np.ndarray` —
  dtype is `np.uint16` or `np.float32` depending on Siril's internal bit depth.
  `preview=True` returns an 8-bit **autostretched** rendering, computed by Siril itself
  (faster than reimplementing autostretch in NumPy) — this is our primary mechanism for
  matching what the user sees on screen (see §7 for STF details).
- **Image lock**: any pixel-data *mutation* (`set_image_pixeldata`, `set_image_mask`,
  etc.) must happen inside `with siril.image_lock():` — required to claim Siril's single
  processing thread; raises `ProcessingThreadBusyError` otherwise. We are **read-only**
  against the loaded image (§45 of the brief — never destructively modify the source),
  so our own usage of `image_lock()` will be minimal/none in normal operation.
- **Correction from real-world testing (2026-08-26)**: `get_image_pixeldata()`'s
  return-array channel-axis convention (channels-first vs. channels-last) and exact
  dtype for `preview=True` were never pinned down from docs alone (the HWC ordering
  quoted above is documented specifically for `FFit.data`, not confirmed for
  `get_image_pixeldata()`'s own return value). This ambiguity turned out to be real:
  the GUI preview rendered incorrectly against an actual plate-solved color image.
  **Mitigation**: `annotation/pixel_utils.py::to_hwc_uint8()` normalizes any mono/RGB,
  channels-first/channels-last, uint8/uint16/float array into a predictable HxWx3 uint8
  array by detecting the channel axis from its size (≤4) rather than assuming a fixed
  position, and is used for both the GUI preview and the export compositing path so
  there is one tested normalization instead of two independent assumptions.

**FITS metadata**: `siril.get_image_fits_header(return_as='str'|'dict')`,
`siril.get_image_keywords() -> Optional[FKeywords]` (typed dataclass — includes
`pltsolvd: bool`, `object`, `instrume`, `telescop`, `focal_length`, `pixel_size_x/y`,
`date_obs`, etc.), `siril.get_image_history() -> list[str] | None`.

All CONFIRMED, verbatim from `Python-API.html`.

## 4. WCS Access

**There is no `get_wcs()` and no direct CRVAL/CRPIX/CD-matrix accessor.** Verified by
exhaustive review of the API reference — no such method exists.

Two supported paths instead:

1. **Coordinate conversion only** (no WCS object exposed): `siril.pix2radec(x, y)` and
   `siril.radec2pix(ra, dec)`. Both explicitly require the image to be plate solved and
   raise `ValueError` otherwise. Sufficient for point transforms but not for building an
   independent `astropy.wcs.WCS`.
2. **Full WCS object, built manually** (the sanctioned pattern for anything needing
   `astropy.wcs.WCS`): pull the raw header via `get_image_fits_header(return_as='str')`
   (or `FFit.header`), then `sirilpy.utility.parse_fits_header(header_text)` — whose
   docstring states it "Handles Siril's newline-separated FITS header format and
   converts it to a dictionary **compatible with astropy.wcs.WCS**" — then construct
   `astropy.wcs.WCS(header_dict)` ourselves.

**Plate-solve status check**: `siril.get_image_keywords().pltsolvd` (`bool`) is the
documented way to verify plate-solve status without relying on catching exceptions from
`pix2radec`/`radec2pix`.

**Decision for our architecture**: build our own `astropy.wcs.WCS` via
`parse_fits_header()` + `WCS(header_dict)`, per §7 of the brief's preference for
`astropy.wcs.WCS`. Use `pix2radec`/`radec2pix` only as a cross-check / fallback, not as
the primary transform, since a real `WCS` object gives us vectorized array transforms
(needed for efficient collision-avoidance/label-placement math) that point-by-point RPC
calls to Siril would not.

Confirmed by both research agents independently, and corroborated by real prior art:
`utility/Svenesis-AnnotateImage.py` builds its own `astropy.wcs.WCS` from the FITS
header (`extract_wcs_from_header`) rather than relying on any sirilpy WCS accessor,
because none exists.

## 5. Prior Art: Real Siril Python Scripts

Repository: **`gitlab.com/free-astro/siril-scripts`** (confirmed exact location; flat
structure, categories `RC-Astro/`, `StarNetAstro/`, `SyQon/`, `VeraLux/`, `core/`,
`preprocessing/`, `processing/`, `utility/`). No manifest/index format — Siril discovers
scripts by scanning script-storage directories for `.py`/`.ssf` files.

**Hard packaging constraint, confirmed verbatim** (`authors.html`):

> "Scripts should be single-file scripts... the multiple files would need to be combined
> into a single file for submission to the scripts repository."

This directly affects our architecture (§ ARCHITECTURE.md, §Distribution): we develop
modularly, but the distributed script must be a single `.py` file, built by inlining
sibling modules at packaging time.

### Directly relevant prior art

- **`utility/Svenesis-AnnotateImage.py`** (Sven Ramuschkat, ~3556 lines) — does almost
  exactly what we're building: plate-solved image → catalog query → configurable
  markers/labels/grid/compass/legend → PNG/TIFF/JPEG export. This is our single most
  important reference. Confirmed via direct source read.
- **`utility/Galaxy_Annotations.py`** (Steffen Schreiber & Patrick Wagner) — SIMBAD-based
  galaxy overlay, independently arrives at the same astroquery-based strategy.
- **`utility/Asteroid_Comet_Finder.py`** (Alexand Salamatov) — SkyBot/JPL Horizons +
  `siril.cmd("show", ra, dec, name)` markers.
- **`utility/Blink_Browse_Filter_Sort.py`**, **`utility/ImageWindow.py`** (Adrian
  Knagg-Baugh) — PyQt6 `QGraphicsView` pan/zoom pattern, directly reusable:

  ```python
  class GraphicsView(QtWidgets.QGraphicsView):
      zoom_factor_base = 1.25
      def __init__(self, *args, **kwargs):
          super().__init__(*args, **kwargs)
          self.setRenderHints(QtGui.QPainter.RenderHint.Antialiasing |
                               QtGui.QPainter.RenderHint.SmoothPixmapTransform)
          self.setTransformationAnchor(QtWidgets.QGraphicsView.ViewportAnchor.AnchorUnderMouse)
          self.setDragMode(QtWidgets.QGraphicsView.DragMode.ScrollHandDrag)
      def wheelEvent(self, event):
          factor = self.zoom_factor_base if event.angleDelta().y() > 0 else 1/self.zoom_factor_base
          self.scale(factor, factor)
  ```

- **`VeraLux/VeraLux_Alchemy.py`** (Riccardo Paterniti) — `QGraphicsScene` +
  `QGraphicsPixmapItem`, `QThread`/`pyqtSignal` worker pattern, `QSettings` persistence.
- **`core/Siril_Catalog_Installer.py`** (Adrian Knagg-Baugh) — proper `QThread` +
  `pyqtSignal` worker pattern; also demonstrates `get_siril_systemdatadir()` usage for
  locating Siril's bundled catalog files.

### Connection / versioning idiom (near-universal across authors)

```python
import sirilpy as s
s.ensure_installed("numpy", "PyQt6", "astropy", "astroquery")
if not s.check_module_version(">=1.1.0"):
    sys.exit(1)
siril = s.SirilInterface()
siril.connect()
siril.cmd("requires", "1.4.0")   # gate on Siril version; hides script from menu if unmet
```

### Threading: two competing real-world patterns

- `Svenesis-AnnotateImage.py` uses **no** `QThread` — it blocks the GUI thread on
  `concurrent.futures.ThreadPoolExecutor` results during catalog queries. Works, but
  freezes the UI during network I/O.
- `Siril_Catalog_Installer.py` and `VeraLux_Alchemy.py` use proper `QThread` +
  `pyqtSignal` workers that emit plain data back to the main thread.

**Decision**: follow the `QThread`/`pyqtSignal` pattern for our own worker code (network
catalog queries, full-resolution export/TIFF write, layout optimization) — per the
brief's explicit responsiveness requirement (§30–31).

**Important gap, confirmed absent from all sources**: no official statement exists on
whether `SirilInterface` itself is thread-safe. No official example calls it from a
background thread. **Decision**: confine all `siril.*` calls to the main thread;
only pure-Python/NumPy/network work moves into `QThread` workers.

## 6. Display Stretch / STF Access

**Confirmed exposed** (this could easily have gone the other way — verified directly):

- `siril.get_siril_stf() -> STFType` — enum: `ASINH_DISPLAY`, `AUTOSTRETCH_DISPLAY`,
  `HISTEQ_DISPLAY`, `LINEAR_DISPLAY`, `LOG_DISPLAY`, `SQRT_DISPLAY`, `SQUARED_DISPLAY`.
- `siril.get_siril_stf_linked() -> bool`
- `siril.get_siril_slider_state(float_range=False)` / `set_siril_slider_lohi(lo, hi)`
- `siril.get_image(preview=True)` / `get_image_pixeldata(preview=True, linked=...)` —
  returns an 8-bit array **already autostretched by Siril**, which is the simplest and
  most faithful way to make our preview match what the user currently sees, without
  reimplementing STF math ourselves.

**Decision**: use `get_image_pixeldata(preview=True)` for the default GUI preview
(§19–20 of the brief), with an independent stretch control (Linear/Auto/Asinh) as a
fallback/override the user can toggle, built from the raw (non-preview) pixel data using
NumPy — satisfying the brief's requirement even in the case where preview reproduction
were imperfect.

## 7. Sending Commands / Structured Results

`siril.cmd(*args)` triggers a command but **has no return value** — confirmed verbatim,
twice, from official docs: commands that only print to the Siril log (rather than
mutate image/sequence state) return nothing useful; structured data must come from
dedicated `get_*` accessor methods.

This directly shapes catalog strategy (§8 below): `conesearch` and `show`, called via
`cmd()`, do not hand structured data back through the Python return value. However,
tracing the actual execution path (Siril's C source, see §8) shows `conesearch -out=`
*does* write a parseable CSV file as a side effect, which our script could read back —
a real, if unofficial, structured-data channel.

## 8. Catalog / Annotation Object Access — the Central Design Question

**`sirilpy` exposes no catalog or annotation API.** We downloaded and grepped the actual
`sirilpy` source (`gitlab.com/free-astro/siril/-/raw/master/python_module/sirilpy/connection.py`,
6011 lines) case-insensitively for `catalog` and `annotation`: **zero matches**. Only
generic, non-catalog methods exist (`cmd()`, `pix2radec()`, `radec2pix()`,
`get_siril_systemdatadir()`, `get_siril_configdir()`).

Four real options were investigated, tracing actual Siril C source where relevant:

### Option A — `conesearch` command
Syntax: `conesearch [limit_magnitude] [-cat=] [-out=file.csv] ...`, catalogs include
`tycho2, nomad, gaia, localgaia, ppmxl, bsc, apass, gcvs, vsx, simbad, aavso_chart, exo,
pgc, solsys`. Requires plate solve.

Traced through `src/core/command.c` (`process_conesearch`) →
`src/io/siril_catalogues.c` (`execute_conesearch`, dispatches an async worker thread) →
but critically, `src/io/siril_pythoncommands.c` calls `processcommand(cmd, TRUE)` —
`wait_for_completion=TRUE` — and `command_line_processor.c`'s `processcommand()` blocks
on `waiting_for_thread()` when the command doesn't return `CMD_NO_WAIT`. **Conclusion:
`siril.cmd("conesearch", ...)` from Python blocks until the query (and any `-out=` CSV
write) completes**, and the CSV is written by the same generic writer used for local
catalog files (§Option C) — i.e. genuinely structured, parseable output. This is a real
channel, verified via source, that **no surveyed prior-art script currently uses** —
worth prototyping in a later phase but not yet proven in production.

### Option B — `show` command
Draws a temporary GUI marker only (`CAT_SHOW` catalog index); returns no data. Confirmed
real usage: `Asteroid_Comet_Finder.py` calls `siril.cmd("show", ra, dec, name)`
fire-and-forget, purely to also mark objects in Siril's own on-screen overlay — useful as
a *supplementary* action, not a data source.

### Option C — Local catalog files, read directly
Confirmed via source (`src/io/annotation_catalogues.c`): built-in catalogs
(Messier/NGC/IC/Sh2/LDN/stars/constellations) live at
`get_siril_systemdatadir()/catalogue/*.csv` (a real, exposed `sirilpy` method for the
directory path); user catalogs live under the user config dir. Format: plain
header-driven CSV (`name,ra,dec,diameter,mag,alias` for Messier/NGC/IC/Sh2; no `mag` for
LDN; `pmra,pmdec,mag,alias` for stars). **Gaps**: no object-type/classification column
for any deep-sky catalog, and common-name (`alias`) coverage is good for Messier but
sparse for NGC/IC. Not a documented, versioned public contract for third parties — an
internal engine data path we'd be reading opportunistically, even though the *directory
path* itself comes from a real sirilpy accessor.

### Option D — Independent queries (Astropy/astroquery: VizieR + SIMBAD)
**This is what every real, feature-complete prior-art script actually does.**
`Svenesis-AnnotateImage.py`, `Galaxy_Annotations.py`, and `Asteroid_Comet_Finder.py` —
three independent authors — all converged on `astroquery` rather than any Siril-native
path:

- VizieR `VII/118` (NGC 2000.0 — Messier/NGC/IC), `VII/20` (Sharpless), `VII/220A`
  (Barnard), `V/50` (Yale Bright Star Catalog)
- SIMBAD TAP queries for common-name resolution and object type

This gives object type, magnitude, angular size, and reliable common names — exactly
the fields our data model (§9 of the brief) requires — which local CSVs and `show` do
not fully provide.

### Decision: Hybrid, weighted toward Option D

1. **Primary**: `astroquery` against VizieR + SIMBAD, mirroring
   `Svenesis-AnnotateImage.py`'s proven query set (same catalogs, same TAP pattern for
   common names). This is the only option that supplies object type + reliable common
   names + magnitude + size together, and it's validated by three independent
   implementations.
2. **Secondary / offline fallback**: local CSVs via `get_siril_systemdatadir()` — fast,
   no network dependency, good for a quick magnitude-limited pre-filter or a "no
   internet" mode (the brief explicitly lists "internet unavailable" as an error case to
   handle, §31).
3. **Supplementary, optional**: `siril.cmd("show", ra, dec, name)` fire-and-forget per
   visible annotation, so Siril's own GUI overlay also reflects the current selection —
   pure convenience, never a data source.
4. **Deferred investigation**: `conesearch -out=file.csv`. Real and structured per our
   source trace, but unused by any prior art we found; worth a spike once the MVP catalog
   pipeline (astroquery-based) is working, as a potential way to reduce our dependency on
   external network queries for star catalogs specifically.

All catalog providers will sit behind a common `CatalogProvider` interface (see
ARCHITECTURE.md) so Option D can be the shipped default while A/C remain pluggable
without touching the rest of the app — directly satisfying the brief's "extensible
catalog configuration" requirement (§13).

## 9. ICC / Color Management

Confirmed exposed:

- `siril.get_image_iccprofile() -> bytes | None` — raw ICC bytes; docs note you need
  e.g. Pillow to interpret them.
- `siril.get_siril_display_iccprofile() -> bytes | None` — the profile Siril uses for
  on-screen rendering (distinct from the image's embedded profile) — relevant if we want
  our preview to color-match Siril's screen output.
- `FFit.icc_profile` on the object returned by `get_image()`.

**Decision**: read and, where the export format supports it (TIFF/PNG via Pillow), embed
the source image's ICC profile in exported files, to avoid the unintended color shifts
the brief warns against (§24). Full profile *conversion* logic is out of scope for MVP;
passthrough preservation is the achievable, low-risk win.

## 10. Dependency Installation

```python
sirilpy.utility.ensure_installed(*packages, version_constraints=None, reinstall=False)
```

Confirmed rules (verbatim from `authors.html`):

- `numpy` is pre-installed (a `sirilpy` dependency itself) — no `ensure_installed()` call
  needed for it.
- All other packages (**PyQt6, astropy, astroquery, Pillow, tifffile**) must go through
  `ensure_installed()`.
- **Only `>=` version constraints** — never `==`/`<=` — because all Siril Python scripts
  share one venv; pinning would create cross-script conflicts.
- Documented "known good" list (installs cleanly across OSes) includes: `astropy`,
  `astropy-healpix`, `astroquery`, `matplotlib`, `numpy`, `opencv-python`, `pandas`,
  `photutils`, `pillow`, `pyQt6`, `scipy`. `tifffile` is not on the explicit list but is
  used successfully in an official example.

Our script will call `ensure_installed("PyQt6", "astropy", "astroquery", "Pillow",
"tifffile", version_constraints=[">=6.4", ">=5.3", ">=0.4", ">=10.0", ">=2021.7"])` (exact
floors to be pinned once we start implementation and can test against real environments).

## 11. Export

**`sirilpy` provides exactly one save helper, and it is FITS-only**:
`siril.save_image_file(data, header=None, filename=None) -> bool`.

For PNG/JPEG/TIFF (our actual requirement), there is no sirilpy helper. Two paths exist:

1. Push data back into Siril's loaded image + `siril.cmd("savepng"/"savejpg"/"savetif")` —
   rejected for our use case, since this only ever operates on Siril's *currently loaded*
   image, not our independently-composited annotated image.
2. **Plain Python file I/O** — Pillow (`PIL.Image.fromarray(...).save(...)`) for
   JPEG/PNG/8-bit TIFF, `tifffile` for 16-bit TIFF — both explicitly sanctioned via
   `ensure_installed()`. This is our chosen path.

**Decision, per §22 of the brief**: the export renderer is independent of the preview
renderer. It re-runs annotation placement math against the *native* image resolution
(not the GUI preview's scaled resolution) and composites onto a full-resolution buffer
only at export time — never holding multiple full-resolution floating-point copies
simultaneously (§36).

## 12. Compatibility: Siril 1.4 vs 1.5

- Python scripting has been experimental since introduction (1.3.5-dev) and remains so
  through 1.4 and into 1.5.
- Explicit commitment (verbatim): "we will try very hard to avoid script-breaking
  changes to the API released with 1.4.0 throughout the stable 1.4 series, some parts of
  the API may evolve during the 1.5 development cycle." → **target 1.4.x as the stable
  floor; treat 1.5-dev as a moving target.**
- Concrete gated item: `tkinter`/`tksiril` removal before 1.6.0 — irrelevant to us since
  we're PyQt6-only from the start.
- Version-gating mechanisms, both confirmed: `siril.cmd("requires", "1.4.0")` (hides the
  script from the menu entirely if unmet) and `sirilpy.check_module_version(">=x.y.z")`
  / `needs_module_version()` (module-level gate, does not hide the script).
- **Decision**: call `siril.cmd("requires", "1.4.0")` at startup as our floor, with a
  clear error dialog if it fails rather than a silent crash (§31).
- No single comprehensive 1.4→1.5 sirilpy changelog was found as one document; individual
  "Added: vX.Y.Z" annotations exist per-method in the API reference.
- **Correction from real-world testing (2026-08-26)**: the implementation originally
  also gated on `sirilpy.check_module_version(">=1.1.0")`, using the "1.1.14" figure
  from §1. That figure came from the ReadTheDocs **"latest"** branch, which tracks Siril
  **1.5-dev** — not what actually ships with 1.4.x stable. Testing against a real Siril
  **1.4.4** install failed immediately with "requires sirilpy >=1.1.0, but the running
  Siril provides an older version." This matches other evidence already in this report
  that was under-weighted at the time: `siril-scripts/utility/Galaxy_Annotations.py`
  gates on `check_module_version('>=0.6.37')` for "Siril 1.4.0 Beta 2" — nowhere near
  1.1.x. **The module-version gate has been removed entirely.** We have no reliable,
  confirmed sirilpy version number for the 1.4.x stable channel, so rather than guess
  another number, the only enforced gate is the documented `requires` command check
  (confirmed working against real 1.4.4), and any individual sirilpy call this codebase
  depends on that turns out to be missing on an older install surfaces as a normal error
  dialog at the call site instead of an upfront version assumption. Lesson for future
  compatibility decisions in this project: prefer the **`stable`** ReadTheDocs branch
  over `latest` when picking any version floor, and treat single data points from `latest`
  as 1.5-dev-only unless cross-checked against `stable` or real prior-art code.

## 13. Explicitly Unresolved / Not Confirmed

These items could not be verified from public documentation or accessible source, and
should not be assumed:

1. The exact mechanism (env var / argv / fixed socket-or-pipe path convention) Siril
   uses to hand connection info to a spawned script process — not publicly documented.
   Not a blocker: `siril.connect()` handles this internally.
2. Whether `SirilInterface` is safe to call from a non-main thread — no statement either
   way. We mitigate by never calling it off the main thread (§5 decision above).
3. A single canonical 1.4→1.5 `sirilpy` API diff.
4. Whether `conesearch`/`show` have any special-cased behavior beyond the general
   "`cmd()` returns nothing; use `get_*` accessors, except confirmed via source trace for
   `conesearch -out=`" rule established in §8/§Option A.
